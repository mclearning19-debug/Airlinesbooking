# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Commands

```bash
npm run dev      # Express + Vite (middleware mode, HMR) on http://localhost:3000
npm run build    # vite build -> dist/
npm start        # production: Express serves /api and dist/ (node server/index.js --prod)
```

- Requires Node 22+ (`--env-file-if-exists`, global WebSocket for the Neon driver). Config comes from `.env` (see `.env.example`): `DATABASE_URL` (Neon pooled connection string, required, server exits without it), `PORT`, `BETTER_AUTH_SECRET` (random; required in production) and `BETTER_AUTH_URL` (public origin; in production falls back to Render's `RENDER_EXTERNAL_URL`, the server exits if neither is set). `render.yaml` is the Render Blueprint (health check `/api/health`; `DATABASE_URL` is prompted, `BETTER_AUTH_SECRET` generated).
- There is no test suite or linter (so no single-test command). Verify server changes with `node --check server/*.js` and by hitting the API with curl (`/api/health` checks DB connectivity). Verify frontend changes with `npm run build`.
- curl against `/api/auth/*` must send `-H "Origin: http://localhost:3000"` (Better Auth rejects foreign origins with 403) and use a cookie jar (`-c`/`-b`) to stay signed in. Per-user endpoints return 401 without the session cookie, so the seat-race check needs a signed-in cookie: fire 4 concurrent identical `POST /api/bookings` and expect `[201, 409, 409, 409]`.
- Changes under `server/` need a server restart; Vite only hot-reloads `src/`.
- Windows: stopping `npm run dev` from a background shell can leave the child `node` process alive and holding port 3000 (and the HMR port 24678), so a "restarted" server may still be the old code. Check with `Get-NetTCPConnection -LocalPort 3000` and kill stale `node` processes before trusting results.
- `DATABASE_URL` points at a real Neon database. Clean up any test rows you create: delete test bookings first (they reference `"user"`), then the throwaway users (sessions and accounts cascade).

## Architecture

Single deployable: one Express process (`server/index.js`) serves the REST API under `/api` and the React SPA. In dev it mounts Vite as middleware (`appType: 'spa'`). In prod it serves `dist/` with an `index.html` fallback for client routes. Don't introduce a separate frontend server or a second process; this is a deliberate requirement.

**Database (Neon Postgres, `server/db.js`)**: uses `Pool` from `@neondatabase/serverless` (WebSocket), not the HTTP `neon()` driver, because writes need interactive transactions (`transaction(fn)` helper). There is no migration tool: `migrate()` runs on every startup under an advisory lock, executes `server/schema.sql`, and seeds `server/data/seed.js` with `ON CONFLICT DO NOTHING`.
- Schema changes must stay idempotent (`CREATE ... IF NOT EXISTS`, `ALTER TABLE ... ADD COLUMN IF NOT EXISTS`).
- Editing the seed file does not update rows already in the database.
- `numeric` columns come back as strings, so queries cast with `::float8` or the code wraps them in `Number()`.

**API (`server/api.js`)**: Express 5, so async handlers that throw/reject reach the router's error handler. Throw `HttpError(status, message)` for client errors. Responses are `{ error }` on failure. `express.json()` is mounted inside the API router (not app-level) so JSON parse errors are handled there.
- Domain: flight booking (seat-capacity variant of slot booking). Tables: `airports`, `flights`, `bookings`, `booking_passengers`. The one transactional write is `POST /api/bookings`: it ignores client prices/totals/status, recomputes fares from `flights.base_price` and `RULES.cabins`, and inserts the booking and passengers in one transaction. Double-booking is prevented by the partial unique index `passengers_seat_unique (flight_id, seat) WHERE active`; its violation (23505) maps to 409 naming the seat. Cancelling sets `active = false`, which frees the seats, and is refused (409) inside `RULES.cancelHoursBefore` of departure.
- Flights are generated by `generateFlights()` in `server/data/seed.js` for the next `RULES.searchDays` days on every start (bulk insert, ON CONFLICT DO NOTHING), so the schedule rolls forward. All aircraft share the one seat layout in `RULES.cabins` (`seatMap()` in `server/config.js`).
- Timestamps are stored as UTC and displayed in the airport's timezone (`airports.timezone`). The search `date` is the local date at the origin airport.

**Auth ([Better Auth](https://www.better-auth.com), email + password)**: configured in `server/auth.js`, mounted by `server/index.js` at `/api/auth/*splat` *before* any body parser, in the same process. It shares the app's Neon `Pool`. Its tables (`user`, `session`, `account`, `verification`) are hand-written in `server/schema.sql` (camelCase quoted columns, do not rename them); there is no Better Auth CLI step. `auth.js` and `api.js` are imported dynamically *after* `migrate()` in `server/index.js`: Better Auth checks for its tables as soon as it loads, so a static import fails on a fresh database. Don't "tidy" that back into static imports.
- In handlers, call `await requireUser(req)` (`server/api.js`) and scope every per-user query with `user.id`. Never trust a user id from the body, query or headers. Browsing endpoints stay public.
- The session is an httpOnly cookie, so the frontend stores nothing. `src/services/auth.js` exports the client (`useSession`, `signIn`, `signUp`, `signOut`); wrap protected routes in `<RequireAuth>` (UX only, the server enforces access). A 401 from `/api` means "sign in".
- Per-user tables reference `"user"(id)` (text), e.g. `user_id text NOT NULL REFERENCES "user"("id")`. `"user"` is a reserved word: always quote it.
- Bookings belong to a user (`bookings.user_id`). Rows created before sign-in existed have only the old anonymous `client_id` and `user_id` NULL: nobody can see or cancel them, but their seats stay held.

**Business rules** live only in `server/config.js` and reach the UI through `GET /api/config`. Don't re-declare them in `src/`.

**Frontend (`src/`)**: React 18 + react-router-dom v6.
- All server calls go through `src/services/api.js` (same-origin `fetch`). Components never call `fetch` directly.
- Every fetching page uses `src/hooks/useAsync.js` and renders loading, error-with-retry and empty states.
- `src/services/storage.js` (localStorage wrapper, keys prefixed `airline-booking:`) is currently unused: sessions live in a cookie, so nothing is stored client-side.
- Cached client snapshots can go stale; the server's checks are what count.
- Search criteria (`from`, `to`, `date`, `passengers`) live in the URL search params.
- Browsing (Home, Flights, seat maps) is public; Book, MyBookings and BookingDetail are behind `<RequireAuth>`. Flow: Home (search) -> Flights (results) -> Book (seat map + passengers + contact) -> BookingDetail; MyBookings lists and cancels. There are no image assets.

## Deployment

A multi-stage `Dockerfile` (node:22-alpine, runs `node server/index.js --prod`, port 3000) is included as an alternative to Render's native Node build; Render does not use it, but the Azure deployment below does. Production mode is `NODE_ENV=production` or the `--prod` flag (`server/env.js`).

Live on Render (free web service `airline-booking`, Ohio): https://airline-booking-to3e.onrender.com. Source is the public GitHub repo `mclearning19-debug/Airlinesbooking` (`origin`, branch `main`). The service has auto-deploy on, so **every push to `main` redeploys production**; verify locally first.
- The service was created through the Render API, not from `render.yaml`, so changing `render.yaml` does not change the running service. Change build/start commands and env vars in the Render Dashboard (or API). `render.yaml` is only for creating a new service from a Blueprint.
- Production env vars live only in Render: `DATABASE_URL`, `BETTER_AUTH_SECRET` (different from dev), `NODE_VERSION=22`. `BETTER_AUTH_URL` is intentionally unset: `server/auth.js` falls back to Render's `RENDER_EXTERNAL_URL`. Set it only for a custom domain, otherwise sign-in fails with `INVALID_ORIGIN`.
- Production (Render and Azure) currently shares the same Neon database as local dev, so test users and bookings made locally are visible in production (and vice versa). Delete test data everywhere.
- Free plan sleeps after 15 minutes idle; the first request takes about a minute. The migration re-runs on each start (idempotent).
- After a deploy, check `/api/health`, a SPA deep link such as `/bookings`, and a sign-up/booking round trip on the live URL.

### Azure (second deployment, Azure Container Apps)

Live at https://airline-booking.orangestone-ac8d8541.eastus.azurecontainerapps.io. It runs the repo `Dockerfile`, deployed manually with the Azure CLI: **pushing to `main` does not redeploy Azure** (there is no CI for it).
- Subscription "Azure subscription 1", tenant `886da1f3-d5b5-4f86-b244-e6314d24b6a5`, resource group `airline-rg` (eastus). Resources: Container App `airline-booking`, environment `airline-env`, Basic container registry `cad1efcdf2cdacr`, and a Log Analytics workspace. `az group delete -n airline-rg` removes everything. The subscription allows only one Container Apps environment per region.
- Scale 0-1 replicas, so the first request after idle is a cold start.
- Env vars on the app: `NODE_ENV=production`, `DATABASE_URL` and `BETTER_AUTH_SECRET` (both `secretref:` to Container App secrets `dburl` and `authsecret`; the auth secret is separate from dev and Render), and `BETTER_AUTH_URL=https://<app fqdn>`. `BETTER_AUTH_URL` is required here: there is no `RENDER_EXTERNAL_URL` fallback, so without it the server exits. Update it if the FQDN or domain changes, otherwise sign-in fails with `INVALID_ORIGIN`.
- Redeploy after code changes (run from the repo root, PowerShell, `az` signed in via `az login --use-device-code`):
  1. `az acr build -r cad1efcdf2cdacr -t airline-booking:<new-tag> --no-logs .`
  2. `az containerapp update -n airline-booking -g airline-rg --image cad1efcdf2cdacr.azurecr.io/airline-booking:<new-tag>`
- Windows CLI gotchas: `az containerapp up --source .` crashes with `UnicodeEncodeError` (cp1252 vs the build log's checkmark) while streaming the build, so use `--no-logs` as above. `az` runs through `cmd`, so a value containing `&` (the Neon `DATABASE_URL` has `channel_binding=...&...`) truncates the command and drops every later argument; wrap such values in embedded quotes (`"`"dburl=$db`""` in PowerShell) and check the result with `az containerapp show ... --query "properties.template.containers[0].env"`. Use `--no-wait` and poll for `az containerapp env create`, since an interrupted create leaves the environment stuck in `Waiting`.
- Check logs with `az containerapp logs show -n airline-booking -g airline-rg --type console --tail 40`.
